# Live sync implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Two phones (or a phone and a laptop) share one planner through a free Supabase project with no logins: pair once with a code, edit on either, see changes within seconds, keep working offline.

**Architecture:** A pure sync engine (`src/lib/syncEngine.ts`) written against small `LocalStore`, `Transport` and key-value interfaces, so it is tested with two simulated phones and a fake server. A thin runtime binds it to `tableStore`, `localStorage` and the real Supabase transport (`fetch` to `/rest/v1/rpc/...` plus a Realtime Broadcast socket). Rows are encrypted per row before upload; the server only stores ciphertext and applies last-write-wins by `updated_at`.

**Tech Stack:** React 18, TypeScript, Vite 6, Vitest 2 + RTL (jsdom), Web Crypto (`crypto.subtle`), no new npm dependencies, CI on GitHub (`/home/claude/ci.sh`); the sandbox cannot reach Supabase.

**Spec:** `docs/superpowers/specs/2026-10-31-live-sync-design.md` (server SQL in `docs/supabase/setup.sql`)

## Global Constraints

- Pairing code: 24 characters, alphabet `ABCDEFGHJKMNPQRSTUVWXYZ23456789` (31 letters/digits), shown as 6 groups of 4 separated by `-`; input is normalised (case, spaces and dashes ignored).
- Household id = hex SHA-256 of `"lp-household|" + code` (normalised, no dashes); key = HKDF-SHA256 of the code with info `"lp-key"` -> AES-256-GCM; fresh 12-byte IV per row, base64 `iv + ciphertext`; the row's `tbl|id` is bound as additional authenticated data.
- Server limits: push at most 500 rows (client sends batches of 200); pull returns at most 1000 rows per call (client keeps pulling until a call returns fewer than 1000); payload at most 65536 characters.
- Timing: push debounce 1 s after a local change; poll every 20 s while the app is visible; also pull on start, on return to the app and when the browser comes back online; failure backoff 10 s doubling up to 5 min; Realtime channel `hh:<household id>`, event `changed`.
- Local keys: `lp.sync.code`, `lp.sync.meta`, `lp.sync.cursor`, `lp.sync.dirty`, `lp.sync.clock`. Row data in `lp.data.*` is never modified by sync bookkeeping, so backups and exports are unchanged.
- Not synced: receipt photos, PIN, theme, `lp.me`, other `lp.*` settings. All tables in `TABLES` sync, including `members`.
- Supabase URL `https://ifnlknnyemllrcwkzmsa.supabase.co` and publishable key `sb_publishable_BI2eDyplltda-cEWtBKj8A_kEJ-MirM` live only in `src/lib/syncConfig.ts` (public by design). Never use or ask for a service_role/secret key.
- View-only mode never starts sync. Existing tests and labels keep working; every push needs CI green (tests and typecheck).
- Joining a phone first downloads a backup file of what it holds, then replaces its data with the shared planner.

## Review Focus

- Clock skew: a phone whose clock is behind still wins over a change it has already seen (monotonic `updated_at`). Tested in Task 3.
- Delete versus edit on two phones: whichever has the later `updated_at` wins on both phones, and a delete is never undone by an older edit. Tested in Task 4.
- A pull that returns exactly 1000 rows must be followed by another pull. Tested in Task 4.
- A pulled row that fails to decrypt (wrong code or tampering) is skipped and counted, never applied, and does not stop the rest. Tested in Task 4.
- Storage full while applying remote rows: the cursor does not advance, status is `error`, and the next sync retries the same rows. Tested in Task 4.
- Applying remote rows never marks them dirty (no echo loop), and a push that fails keeps its rows dirty across restarts. Tested in Tasks 3 and 4.

### Task 3: Engine, local changes and push

**Files:** Create `src/lib/syncEngine.ts`; Test `tests/syncEngine.test.ts` (with in-test `FakeBackend`, `MemoryLocal`, `MemoryKV` helpers).

**Interfaces:**
- Produces:
  - `interface SyncRow { tbl: string; id: string; payload: string | null; deleted: boolean; updated_at: number; seq?: number }`
  - `class TransportError extends Error { kind: 'offline' | 'server' }`
  - `interface Transport { push(household: string, rows: SyncRow[]): Promise<void>; pull(household: string, after: number): Promise<SyncRow[]>; ping(): Promise<void>; subscribe(household: string, onChanged: () => void): () => void }`
  - `interface LocalStore { getAll(): Record<string, Row[]>; apply(tables: Record<string, Row[]>): void; onLocalChange(cb: (table: string, prev: Row[], next: Row[]) => void): () => void }`
  - `interface KV { get(key: string): string | null; set(key: string, value: string): void }`
  - `interface SyncStatus { state: 'idle' | 'syncing' | 'offline' | 'error'; lastSyncedAt: number | null; pending: number; message?: string }`
  - `interface SyncResult { pushed: number; pulled: number; rejected: number }`
  - `class SyncEngine { constructor(opts: { household: string; key: CryptoKey; local: LocalStore; transport: Transport; kv: KV; now?: () => number }); start(): void; stop(): void; markAllDirty(): void; syncNow(): Promise<SyncResult>; get status(): SyncStatus; onStatus(cb: (s: SyncStatus) => void): () => void }`
  - `start()` subscribes to `local.onLocalChange`; every changed or removed row id is stamped `updated_at = max(now(), clock + 1)`, recorded in `lp.sync.meta` (`{ [tbl]: { [id]: { u: number, d?: 1 } } }`), added to `lp.sync.dirty`, and the clock saved in `lp.sync.clock`. Changes are found by comparing prev and next rows by id with JSON equality.

- [ ] **Step 1: Write failing tests:** an insert, an edit and a delete each mark exactly that id dirty (edits that change nothing do not); `markAllDirty` marks every local row; `syncNow` pushes dirty rows encrypted (`payload` is not readable text and decrypts to the row), deletes as `deleted: true, payload: null`, in batches of at most 200 (450 rows -> 3 calls), then clears them from dirty; a failing push (`TransportError offline`) leaves rows dirty, sets status `offline`, `syncNow` does not throw, and a new engine over the same `KV` still has them dirty and pushes them; a `server` error sets status `error` with a message; clock skew: with `now()` far behind a remote `updated_at` the engine has seen, a new local edit gets an `updated_at` greater than it; the status `pending` equals the dirty count.
- [ ] **Step 2: Run;** FAIL. **Step 3: Implement** the engine core (this task covers `start`, `markAllDirty`, change tracking, push batching, status); `syncNow` here may pull nothing yet (Task 4 adds pulling). **Step 4: Run;** PASS. **Step 5: Commit** `feat: sync engine change tracking and push`.

### Task 4: Engine, pull, merge and replace

**Files:** Modify `src/lib/syncEngine.ts`; Test `tests/syncEngine.test.ts`.

**Interfaces:**
- Consumes: Task 3 types. Produces: `syncNow()` now pulls after pushing (cursor in `lp.sync.cursor`, loops while a call returns 1000 rows); `replaceFromRemote(): Promise<{ pulled: number }>` (pull from 0, build every table in `TABLES`, `local.apply` once, reset meta from remote, clear dirty, set cursor); `SyncResult.rejected` counts undecryptable rows.

### Task 5: Real transport

**Files:** Create `src/lib/syncConfig.ts`, `src/lib/syncTransport.ts`; Test `tests/syncTransport.test.ts`.

**Interfaces:**
- Produces: `SYNC_URL`, `SYNC_KEY` constants; `createSupabaseTransport(opts?: { url?: string; key?: string; fetchImpl?: typeof fetch; WebSocketImpl?: typeof WebSocket }): Transport`.
- `push` -> `POST {url}/rest/v1/rpc/sync_push` body `{ p_household, p_rows: [{ tbl, id, payload, deleted, updated_at }] }`; `pull` -> `POST .../rpc/sync_pull` body `{ p_household, p_after }`, mapping `row_id` to `id`; `ping` -> `POST .../rpc/sync_ping`; headers `apikey` and `Authorization: Bearer <key>`, `Content-Type: application/json`. A rejected `fetch` or a status 0/502/503/504 -> `TransportError('offline')`; any other non-2xx -> `TransportError('server')` with the server message.
- `subscribe` opens `wss://<host>/realtime/v1/websocket?apikey=<key>&vsn=1.0.0`, joins topic `realtime:hh:<household>` with broadcast config, sends a heartbeat every 25 s, calls `onChanged` for an incoming `broadcast` event named `changed`, reconnects with backoff after a close, and returns an unsubscribe that closes it. The broadcast on our own push is sent through the same socket (`event: 'changed'`) by an extra method `notify(household)` on the returned object.

- [ ] **Step 1: Write failing tests with a stub `fetch` and a stub WebSocket class:** request URLs, headers and bodies exactly as above; `pull` maps rows; network failure and 503 -> offline; 400 with `{message}` -> server error carrying the message; `subscribe` sends the join, heartbeats on a fake timer, calls `onChanged` on a `changed` broadcast and ignores others, reconnects after close, stops after unsubscribe; `notify` sends a broadcast frame.
